DETERMINISTIC SYSTEM MAP

System map

The application boundary with its navigation pages inside, the one transport core that owns the pool, lock and socket every page competes for, the client extensions that route through it, the namespaces it dispatches at the gateway, the on-device engines, the event bus and its subscribers, and the external systems orbiting the application. Every node deep-links to its source; the constructions the map assumes are declared as invariants and checked on every build.

Extracted by static source rules, explained by architecture/interplay/overlay.json, and gated by architecture/interplay/invariants.json. Edges are ownership, lifecycle, and wiring—not runtime topology or live connection counts.

STATIC OWNERSHIP & LIFECYCLE CLUSTERS

Connections & streams

Deterministic pockets group stored resources, task handles, and mechanically recognized lifecycle operations by component and enclosing owner type.

These pockets are static clusters, not runtime topology. Cardinality describes source fields, never live connection counts.

DETERMINISTIC BOUNDARY EVIDENCE

External systems

Systems outside the Swift source that Portal talks to or runs on, declared in architecture/config.json and attributed to components by source signatures. Descriptions are specified; usage counts and evidence lines are observed.

A signature match proves a supported source form is present at the cited line—not that the system is reached at runtime, and not how often.

DETERMINISTIC PERSISTENCE EVIDENCE

Data stores

Store, cache, inventory, and ledger types recognised by name, with the persistence mechanism and on-disk artifact names observed in the type body, its same-file extensions, and namesake helper types.

“Unobserved” means no supported persistence API appears in those bodies—the store is in-memory or delegates elsewhere. It is not a claim that nothing is persisted.
